# GraphWiki RAG 구조

2026-08-06 작성 · 코드 기준: `src/lib/rag/compose.ts` · `src/lib/fuseki/client.ts` ·
`src/lib/agent/tools.ts` · `src/lib/llm/embed.ts`

## 한 장 요약

자연어 질문 하나가 들어오면 **LLM은 검색어만 뽑고, 실제 쿼리는 전부 검증된 코드 템플릿**이
만든다. 검색은 세 갈래(그래프 · 위키 부분문자열 · 벡터 의미검색)로 나가고, 모은 근거를
글자 예산 안에서 잘라 LLM에게 넘겨 "근거에 없는 것은 쓰지 않는" 조건으로 문서를 생성한다.

```
사용자 자연어 질문
      │
      ▼ ① 용어 추출 (LLM, qwen3-32b)
["글리세롤", ...]        일반명사·조사 제거 규칙. lib/rag/compose.ts extractTerms()
      │
      ├─────────────┬──────────────────┐
      ▼ ②-a         ▼ ②-b              ▼ ②-c
  그래프 검색      위키 부분문자열       벡터 의미검색
  (Fuseki 3소스)   (Postgres)          (pgvector)
      │             │                  │
      ▼ ③ 근거 수집·예산 절단 (그래프 12,000자 + 위키 3,600자)
      ▼ ④ 문서 생성 (LLM) — "근거에 없으면 쓰지 마라, 출처는 ## 참고에 [[링크]]"
      ▼ ⑤ NDJSON 스트리밍 → 완성 시 자동 저장 (pageType: synthesis)
```

`/ask`(compose)는 이 순서가 **고정**이고, `/chat`(에이전트)은 같은 검색기를 LLM이
도구로 골라 쓴다는 차이만 있다.

## ① 용어 추출 — `extractTerms()`

- LLM에게 SPARQL을 쓰게 하지 않는 이유: 소스 3개의 어휘·그래프 구조가 제각각이고
  사내 vLLM은 guided decoding이 없어 틀린 쿼리를 조용히 만든다. 그러면 "0건"이
  "데이터 없음"인지 "쿼리 오류"인지 구분이 안 된다 — 최악의 실패 모드.
- 그래서 LLM 몫은 `["용어1", "용어2"]` 추출까지. 쿼리는 코드가 만든다.
  같은 질문 → 같은 조회 (재현성).
- 구조화 출력은 `lib/llm/json.ts`가 평문 파싱 + zod 검증으로 처리한다
  (`generateObject` 금지 — vLLM이 지원 안 함).

## ② 검색 세 갈래

### ②-a 그래프 검색 — `fuseki/client.ts searchGraphs()`

| 항목 | 내용 |
|---|---|
| 대상 | ejkim(30303) · kakao(30301) · seunghoon(30310), 병렬 |
| 1차 | `rdfs:label` CONTAINS — 싸다 |
| 2차 | 1차가 빈손이면 리터럴 전문 스캔(`textHits`). 소스별 독립 판단 |
| 어휘 차이 | 관계 네임스페이스·표시명 술어는 `ontology/source.ts`에서만 흡수 |
| 장애 격리 | 소스별 성패 분리(`sources[].ok`). 죽은 소스 60초 차단기. 실패는 "확인 못 함"으로 문서에 명시 |
| 후속 | 찾은 개체 상위 6건의 속성(`attributesFor`)과 이웃 관계(edges)를 근거로 수집 |

### ②-b 위키 부분문자열 검색 — `compose.ts searchWiki()`

- 용어가 **제목·요약·본문**에 나오는 위키 문서를 용어별 3건까지, 용어별 병렬 질의.
- 매칭 지점 앞뒤 600자 발췌. 사람이 쓴 문서(user/agent)를 온톨로지 적재본보다 우선
  (적재본은 그래프 조회와 중복되므로).
- 한국어라 부분문자열이 기본이다 — tsvector는 한국어 토크나이저가 없고 pg_trgm은
  2~3자 질의(가장 흔함)에서 인덱스를 못 탄다.

### ②-c 벡터 의미검색 — `llm/embed.ts` + pgvector

- embeddinggemma(768차원, 사내 Ollama `192.168.0.152:11434`) 임베딩,
  pgvector hnsw 코사인 인덱스.
- 신규·수정 문서는 저장 시 자동 임베딩(embed-on-save). 기존 문서는 백필 필요:
  `node scripts/backfill-embeddings.mjs 0`
- 현재 노출: `GET /api/search?mode=semantic` + 채팅 도구 `wiki_semantic_search`.
  `/ask` 파이프라인 결합은 백필 후 검토 (동의어 문제 해소용 — "글리세린"↔"글리세롤").

## ③ 근거 수집과 예산

qwen3 컨텍스트 32k 토큰(한국어 ≈ 1.5자/토큰)이 절대 제약. `compose.ts` 상수:

| 예산 | 값 | 이유 |
|---|---|---|
| `EVIDENCE_CHARS` | 12,000자 | 그래프 근거 전체. 개체당 균등 분배 — 하나가 다 먹으면 나머지 소스 근거가 사라진다 |
| `VALUE_CHARS` | 1,200자 | 속성 값 하나당. extractedText 몇 개면 실측 88,901자가 나왔다 |
| `WIKI_CHARS` | 3,600자 | 위키 발췌 전체 |
| `EVIDENCE_NODES` | 6 | 속성까지 읽는 개체 수 |

## ④ 생성 규칙 — `writeSystem()`

- 근거에 없는 내용 금지, 모르는 것은 "확인되지 않음"
- 출처는 본문 금지, 맨 끝 `## 참고`에만. 위키에 있는 문서는 `[[slug|이름]]` 링크
- 조회 실패한 소스는 참고 절에 명시 — "없다"와 "못 봤다"를 섞지 않는다
- 모델이 규칙을 어기고 본문에 `[ejkim]`을 박는 경우가 실측으로 있어
  `stripInlineSources()`가 후처리로 걷어낸다

## ⑤ 전달·저장

- NDJSON 스트리밍: `terms` → `graph`(소스별 성패 + 위키 히트) → `delta`(토큰) → `done`.
  작성 단계가 전체의 ~95%(실측 233초 중 210초)라 스트리밍이 없으면 빈 화면 4분.
- 완성 시 자동 저장. slug 충돌이면 접미사로 비켜 저장. `pageType: synthesis` ·
  `editSource: agent` — 사람 글과 생성물을 항상 구분한다.

## 현재 한계와 확장 로드맵

지금 구조는 **개체 중심 lookup RAG**다. 못 하는 것: 조건·집계 질의("몇 건?"),
다중 홉 추론, 관계 자체를 묻는 질의, 동의어(부분문자열의 한계).

| 순서 | 작업 | 효과 | 비용 |
|---|---|---|---|
| 1 | 임베딩 백필 → `/ask`에 의미검색 결합 | 동의어·유사 표현 해소 | 배치 몇 시간 + 코드 반나절 |
| 2 | SPARQL 템플릿 라이브러리 확장 (타입 필터 · n-hop 이웃 · 두 개체 간 경로). LLM은 템플릿+슬롯 선택만 | 관계·경로 질의 | 하루 |
| 3 | Text-to-SPARQL (생성 쿼리 + 실행 전 검증 + 재시도) | 표현력 최대 | 현 모델 오류율 감수, 검증 층 필요 |
