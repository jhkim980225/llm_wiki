## 1. 검토안과 실제 구조의 차이 (교정)

검토안의 가정 중 이 프로젝트와 다른 것 세 가지가 판단을 크게 바꾼다.

### 교정 ① 문서 등록 시 Luna가 Entity/Relation을 추출하지 않는다

검토안: `PDF/Excel/Word → Luna 분석 → Entity/Relation 추출 → RDF 변환 → Fuseki 저장`

실제: **그 파이프라인은 이 프로젝트에 없다.** 문서→그래프 구축(온톨로지 생성)은
상류의 별개 프로젝트들(ejkim·kakao·seunghoon 소스)이 수행하고, 이 프로젝트는
완성된 Fuseki 온톨로지를 **읽기 전용**으로 소비한다.

- `src/lib/fuseki/client.ts`(405줄): SELECT 계열 질의만 있고 UPDATE/INSERT/DELETE 없음
- `src/lib/ontology/build.ts`(203줄): 적재(온톨로지→위키 문서 변환)에 LLM import 자체가 없음
- `deploy/k8s.yaml` 주석: "LLM은 채팅·AI 작성에서만 쓴다. **적재 경로는 LLM을 타지 않는다**"

따라서 **문서 등록 비용은 현재 0원**이다. 18만 문서 적재에 LLM이 한 번도 안 불린다.
이 사실이 LightRAG 대체론의 전제("등록 시 추출 비용이 이미 든다")를 무너뜨린다 —
LightRAG로 가면 없던 추출 비용이 **새로 생긴다**.

### 교정 ② Vector 검색은 "확인 필요"가 아니라 이미 있다

검토안 비교표의 "Vector Search: 현재 구현 여부 확인 필요" → **구현돼 있다.**

- 임베딩: 사내 Ollama embeddinggemma 768차원 (`src/lib/llm/embed.ts`)
- 저장·검색: Postgres pgvector, hnsw 코사인 인덱스
- 신규·수정 문서는 저장 시 자동 임베딩(`src/lib/pages/embedding.ts`, embed-on-save)
- 노출: `GET /api/search?mode=semantic` + 채팅 도구 `wiki_semantic_search`

즉 현 구조는 이미 **그래프 + 벡터 + 부분문자열의 하이브리드 검색**이다. 검토안이
LightRAG의 핵심 장점으로 꼽은 "Graph Retrieval + Vector Retrieval 결합"을
자체 구현으로 이미 갖고 있다.

### 교정 ③ "Graph에 없는 원문 세부내용 누락" 문제도 이미 대응돼 있다

검토안 6절의 우려(그래프 추출에서 빠진 원문 정보가 검색 안 됨)는 타당한 일반론이지만,
이 프로젝트는 두 겹으로 막고 있다.

1. **원문이 위키에 있다** — 온톨로지 개체가 Postgres `Page.content`에 문서로 적재돼
   있고(작업본), 부분문자열 검색(`searchWiki`)이 제목·요약·본문을 그대로 뒤진다.
2. **의미검색이 원문을 뒤진다** — pgvector가 동의어·표현 차이("글리세린"↔"글리세롤")를 흡수.

추가로 Fuseki 쪽도 label 검색이 빈손이면 **리터럴 전문 스캔**(`textHits`)으로
폴백한다(`fuseki/client.ts`). "그래프에 구조화되지 않은 텍스트"까지 검색 대상이다.

## 2. 확인사항 답변 (검토안 11절)

| 질문 | 실측 답 |
|---|---|
| Fuseki에 뭐가 저장되나 | 상류 3소스가 구축한 온톨로지(이메일·카카오톡·업무문서, 개체 13.8만·트리플 141만 규모). 이 프로젝트는 읽기만 한다 |
| 정식 Ontology? RDF Schema/OWL? | 소스별 자체 어휘의 RDF. **OWL 추론 없음.** 소스마다 네임스페이스·술어가 달라 `lib/ontology/source.ts`(84줄) 한 곳에서 흡수한다. ejkim은 메일 1건을 여러 노드로 쪼개는 등 품질 편차가 있어 적재가 분신 병합까지 한다(`build.ts`) |
| Fuseki를 다른 서비스도 쓰나 | **그렇다.** 같은 온톨로지 기반의 소스별 RAG API 3종(kakao·ejkim·seunghoon, `docs/소스-rag-api.md`)이 별도 서비스로 운영 중이고 이 앱의 채팅이 호출한다. Fuseki는 회사 공유 원본(System of Record)이다 — `docs/db-roles.md` |
| SPARQL 활용 수준 | 코드 템플릿 고정: ① `rdfs:label` CONTAINS ② 빈손이면 리터럴 전문 스캔 ③ 찾은 개체의 속성·이웃 1-hop 수집. **LLM이 SPARQL을 생성하지 않는다**(재현성·오류 구분 때문, `rag-architecture.md` ①절). 복잡한 traversal·추론 없음 |
| Vector/Embedding 존재? | 있음 (교정 ② 참조) |
| 원문/Chunk 저장 위치 | Postgres `Page.content`(위키 작업본) + Fuseki 리터럴(원본). 별도 청킹 없음 — 검색 시 매칭 지점 앞뒤 600자 발췌, 근거는 글자 예산(그래프 12,000자 + 위키 3,600자)으로 절단 |
| 등록 시 Luna 호출 수 | **0회** (교정 ① 참조). 단, 적재본을 처음 열람할 때 요약(brief) 1회가 지연 생성된다 |
| Ask 1회당 Luna 호출 수 | **2회** — 용어 추출(`extractTerms`) 1 + 문서 생성 1 (`compose.ts`). 채팅은 에이전트라 스텝 수에 따라 가변(도구 호출 포함 보통 2~5회) |
| LightRAG로 대체 시 제거 가능한 것 | 검색기 3갈래와 예산 로직(`compose.ts` 630줄 중 검색·수집부, `fuseki/client.ts` 405줄) 정도. **위키 기능(문서 편집·버전·낙관적 잠금·링크·트리·FLOW)은 LightRAG와 무관해서 전부 남는다** |
| Fuseki를 유지해야 하는 의존성 | ① 회사 공유 원본이라 우리가 없앨 권한이 없음 ② 소스 RAG API 3종이 같은 데이터 기반 ③ 적재 파이프라인(위키 문서 18만 건)의 원천 ④ 출처 추적(어느 소스의 어느 개체) |

## 3. 비교표 교정판

| 영역 | 현 RAG Wiki (실측) | LightRAG |
|---|---|---|
| 문서→그래프 구축 | 상류 프로젝트 담당, **이 앱은 LLM 0회** | LLM 추출 (문서당 수회 호출, 비용 발생) |
| Graph | Fuseki (회사 공유 원본, 읽기 전용) | 자체 Graph Storage (이 앱 전용) |
| Graph 모델 | RDF Triple, 소스별 어휘 | Entity/Relation (느슨함) |
| Graph Query | 검증된 SPARQL 템플릿 (LLM 미생성) | 자체 dual-level retrieval |
| Vector 검색 | **있음** (pgvector + embeddinggemma) | 있음 (기본 기능) |
| 원문 검색 | 부분문자열 + 리터럴 전문 스캔 | Chunk 벡터 검색 |
| 답변 생성 | LUNA (근거 예산 + "근거 없으면 쓰지 마라") | LUNA (자체 프롬프트) |
| 출처 표기 | `[[위키링크]]` + 소스 배지, 문서로 이동 가능 | 문서 번호 각주 (위키 연동 없음) |
| 등록 비용 | 0원 | 문서당 LLM 수회 (18만 건이면 수백만 원 + 직렬 병목) |
| 운영 | 자체 코드 유지보수 | 파드 1개 + 외부 프로젝트 버전 추적 |

## 4. 판단 — ①유지 / ②대체 / ③하이브리드

### ② 전면 대체: 부적절 (근거 명확)

1. Fuseki는 이 앱의 소유물이 아니라 **회사 공유 원본**이다. 다른 서비스(소스 RAG API 3종)가
   같은 데이터를 쓰고 있어 대체 자체가 성립하지 않는다.
2. LightRAG는 위키가 아니다 — 이 앱의 본체(문서 편집·버전·링크·트리·FLOW·캘린더)는
   어차피 전부 남는다. 제거되는 코드는 검색·수집부뿐이다.
3. 등록 비용이 0 → 문서당 LLM 수회로 **역행**한다. 18만 문서 전량은 비용·시간 모두 비현실적.
4. 검토안이 기대한 "Graph 누락 보완(그래프+벡터 결합)"은 이미 자체 구현돼 있다.

### ① 유지: 기본값으로 타당

현 구조는 검토안의 ③하이브리드 그림(정형 그래프 + 비정형 벡터 → LLM)을 이미
구현한 상태다. LightRAG를 붙여서 **새로 얻는 것**이 증명되기 전까지는 ①이 기본값.

### ③ 하이브리드(부분 채택): 조건부 — PoC 비교로 결정

LightRAG가 이길 가능성이 있는 지점은 두 가지뿐이다.

- **관계 확장 검색의 품질** — 우리 그래프 검색은 1-hop(개체 속성+이웃)에서 멈춘다.
  LightRAG의 dual-level retrieval(개체 키워드 + 추상 주제 키워드)이 여러 문서에 걸친
  관계 질문·요약 질문에서 실제로 더 나은 근거를 모으는지.
- **답변 합성 품질** — 같은 근거라도 컨텍스트 구성 방식이 달라 답이 달라질 수 있는지.

PoC 비교(아래 5절)에서 LightRAG가 유형 ③⑤⑥⑦(관계·누락·복합·요약)에서 유의미하게
이기면 → **4번째 검색기**로 채택(저장 시 LightRAG에도 insert, `/ask`·채팅 근거에 결합).
이때도 색인 대상은 사람·AI 문서 + 적재본 일부로 한정하고, 대량 주입이 필요해지면
LLM 추출 대신 **`insert_custom_kg`로 Fuseki 개체·관계를 직접 밀어넣는다**(추출 비용 0인
유일한 현실 경로 — 우리는 그래프가 이미 있으므로 LightRAG의 추출 단계가 필요 없다).

지면 → PoC 파드 제거(k8s 블록 삭제)로 끝. 앱 흔적은 `/lightrag` 실험 탭뿐이다.

## 5. PoC 비교 방법 (이 프로젝트 도구 기준)

현재 상태: LightRAG 파드 가동 중(NodePort 31930, `2026-08-19-poc-design.md` 참조),
색인 4건(실질 2건), 사이드바 `LightRAG` 탭에서 질의 가능.

| 단계 | 방법 |
|---|---|
| 색인 확대 | `py scripts/lightrag-seed.py --limit 30` (또는 `--slug` 지정). 검토안 기준 20~50건 — LUNA 색인 비용은 건당 2~4회 호출이므로 30건 ≈ 100회 내외 |
| 질문 준비 | 30~50개, 유형 7종: ①단일 문서 사실 ②여러 문서 조회 ③사람↔업무↔프로젝트 관계 ④원문 세부 ⑤그래프에 없는 내용 ⑥복합 관계 ⑦요약 |
| 실행 | 같은 질문을 사이드바 `LightRAG` 탭(모드 hybrid 기본, 필요시 5종 비교)과 `AI 작성`(/ask)·`채팅`에 각각 |
| 정답 판정 | `/verify`(RAG 정확도 검증, `docs/rag-정확도-검증-2026-08-07.md` 방식)를 기존 쪽에, LightRAG 답은 동일 기준 수동 대조 |
| 응답시간 | LightRAG 탭이 초 단위 표시. /ask는 스트리밍 완료 시각 |
| 토큰·비용 | OpenAI 대시보드에서 기간별 gpt-5.6-luna 사용량 비교 (색인 전후 구간 분리) |
| 운영 지표 | 코드량(신규 0 vs compose+fuseki ~1,000줄), 파드 수, 장애 격리(소스별 차단기 유무) |

## 6. 결론 요약

- 검토안의 대체론은 "등록 시 LLM 추출 비용이 이미 든다"는 가정 위에 서 있는데,
  이 프로젝트는 **등록에 LLM을 쓰지 않는다**. 전제가 다르다.
- 그래프+벡터 하이브리드 검색도 이미 있다. 따라서 **① 유지가 기본값**,
  LightRAG는 PoC 비교에서 관계·요약 질문 우위를 증명하면 **③ 4번째 검색기로 부분 채택**.
- ② 전면 대체는 Fuseki가 회사 공유 원본인 이상 성립하지 않는다.
- 대량 색인이 필요해지는 시점의 정답은 LLM 재추출이 아니라 `insert_custom_kg`
  온톨로지 직접 주입이다.
