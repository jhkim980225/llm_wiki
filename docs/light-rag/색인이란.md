# 색인(인덱싱)이란 — LightRAG 기준

색인(인덱싱)은 문서를 LightRAG가 읽고 검색할 수 있는 형태로 가공해서 저장하는 작업

색인 = 문서를 LightRAG에 넣어 **질의 가능한 상태로 만드는 작업**. 

단순히 문서 파일을 서버에 업로드하는 것과는 다르다.

# 색인 과정

문서 한 건을 LightRAG에 전송하면 다음 작업이 진행.

1. 청킹
 - 긴 문서를 검색하기 좋은 작은 단위로 나눈다.
 - 이메일 한 건을 여러 문단 조각으로 분리한다.
 - 기준 크기(기본 1,200토큰)보다 짧은 문서는 안 나뉜다 — 청크 1개 = 문서 전체.
 - 상세와 전략 4종은 아래 "청킹 전략" 절.

2. 개체·관계 추출
LLM인 LUNA가 각 조각을 읽습니다.
성진, 김종태 같은 개체를 찾고,
성진이 김종태에게 발주했다 같은 관계를 추출합니다.
이 결과가 그래프의 노드와 엣지로 저장됩니다.

3. 임베딩
각 문서 조각을 1,536차원 숫자 벡터로 변환합니다 (OpenAI text-embedding-3-small —
2026-08-31 사내 Ollama 768차원에서 전환).
사용자가 정확히 같은 단어를 쓰지 않아도 의미가 비슷한 내용을 찾기 위한 작업입니다.

4. 저장
개체와 관계는 그래프 저장소에,
문서 조각과 임베딩은 벡터 저장소에 기록됩니다.
모든 작업이 끝나면 문서 상태가 processed가 됩니다.

색인 안 된 문서는
그래프에 존재 자체가 없어서 질문해도 답변에 안 잡힌다. [파이프라인.md](wiki/파이프라인.md)의
⑥(전송)·⑦(내부 추출) 단계가 이것이다.

LightRAG에 질문했을 때 해당 문서 내용이 답변에 사용되려면 반드시 색인이 완료되어야 합니다.

## 내부에서 벌어지는 일

문서 1건을 `POST /documents/text`로 던지면 LightRAG가 순서대로:

```
원문 텍스트
  │ ① 청킹 — 문서를 일정 크기 조각으로 분할
  ▼
  │ ② 개체·관계 추출 — LLM(LUNA)이 조각을 읽고
  │    "성진", "김종태", "발주했다" 같은 개체·관계를 뽑아
  │    그래프 노드·엣지로 만든다. SUMMARY_LANGUAGE 설정이
  │    여기서 쓰인다(미설정이면 영어로 뽑힘 — 실측으로 당함)
  ▼
  │ ③ 임베딩 — 조각을 벡터로 변환(OpenAI text-embedding-3-small, 1,536차원).
  │    나중에 의미 검색용
  ▼
그래프 저장소 + 벡터 저장소에 기록 → 상태 processed
```

②에서 LLM이 청크마다 여러 번 불리므로 **비용과 시간이 전부 여기서 나온다** —
①청킹은 기계적 절단(밀리초·무료), ③임베딩은 초 단위·거의 무료. 색인이 느리면
범인은 항상 ②다. 동시성 상한(MAX_ASYNC_LLM=8, MAX_PARALLEL_INSERT=4) 기준
실측 분당 4~5건.

## 청킹 전략 (2026-08-31 실측)

`POST /documents/text`의 `chunking` 파라미터로 **문서 넣을 때마다** 전략을 고른다
(서버 설정·재시작 아님). 미지정 시 `fixed_token`.

| 전략 | 동작 |
|---|---|
| `fixed_token` (기본) | 토큰 수로 기계적 절단 — 문장·표 중간도 뚝 자름 |
| `recursive_character` | 문단(`\n\n`) → 줄바꿈 → 문장부호 → 공백 순으로 경계를 찾아 자름 |
| `semantic_vector` | 문장 임베딩 유사도로 주제 전환점을 찾아 자름 |
| `paragraph_semantic` | 제목·문단 구조 단위로 묶음 |

파라미터(실측 확인): `chunk_token_size`(기본 1200) · `chunk_overlap_token_size`(기본 100) ·
`separators`(recursive용 구분자 목록).

```json
{"text": "...", "file_source": "doc-id",
 "chunking": {"strategy": "recursive_character",
              "params": {"chunk_token_size": 800, "chunk_overlap_token_size": 80}}}
```

알아둘 것:
- **겹침(overlap)** — 인접 청크가 경계 부분을 서로 겹쳐 갖는다. 경계에서 잘린 문장도
  한쪽 청크엔 온전히 들어가게 하는 안전장치
- 짧은 문서(기준 크기 이하)는 전략과 무관하게 청크 1개
- **전략을 바꿔도 이미 색인된 문서의 청크는 안 바뀐다** — 삭제 후 재색인해야 반영
- 검색이 "의미 단위로 찾아지는" 건 청킹이 아니라 개체 추출(그래프)과 벡터 유사도가
  하는 일 — 질문 → 개체 매칭 → 그 개체가 든 청크 수집 순서로 동작한다
- GraphRAG는 청크가 커야 추출 맥락이 살아서 일반 벡터 RAG 권장(256~512토큰)보다
  큰 1,200이 기본값이다

## 문서 상태

| 상태 | 뜻 |
|---|---|
| pending | 대기열에 있음 |
| processing | ①~③ 진행 중 |
| processed | 색인 완료 — 질의에 잡힘 |
| failed | 실패 — 그래프에 없음. 삭제 후 재제출해야 함 |

`/lightrag` 화면(확인용)이나 `GET /documents`로 확인한다.

## 우리 파이프라인에서의 위치

```
원본 이메일 → 큐레이션 → wiki/ 문서(reviewed) → [색인] → LightRAG 그래프 → 질의응답
```

- 색인 도구: `scripts/lightrag-wiki-seed.py`(큐레이션 위키) · `scripts/lightrag-seed.py`(운영 위키)
- 색인 대상: `status: reviewed`인 문서만. 프론트매터는 벗겨내고 본문만 전송, `file_source = id`
- 현재 색인: 121건 (wiki 87 + 운영 위키 34), 전부 processed

  레이스로 문서가 그래프에서 조용히 증발한다. `/documents`에서 사라진 것 확인 후 재제출
- ~~emptyDir~~ → PVC 전환 완료(2026-08-31). 파드 재시작해도 색인 유지
- **같은 id 재색인 거부** ("already contains") — 갱신하려면 삭제 후 재제출.
  이 응답은 기존 문서가 failed여도 똑같이 나오므로 "이미 있음 = 성공"으로 착각하지 말 것
- **LUNA 크레딧 소진 시** 색인·질의 전부 실패하며 오류가 "No relevant context"로
  위장된다 — 파드 로그로만 구분 가능
