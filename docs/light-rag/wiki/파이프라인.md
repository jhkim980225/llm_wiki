# wiki/ 데이터 파이프라인

`wiki/` 폴더가 원본 이메일에서 어떻게 만들어지고 LightRAG까지 가는지 전체 순서.
각 문서의 상세 규칙은 따로 있고, 이 문서는 **단계 간 순서와 책임 분리**만 정리한다.

```
① 원본(비정형)          data/sj-help_보낸메일함/Files/*.eml
        │
        ▼
② 추출 (Claude)         이메일 배치로 읽어 회사·사람·제품·날짜·사실을 구조화 텍스트로 뽑는다
        │                — 원본 재조사 없이 재사용 가능하게 배치 단위로 병렬 처리
        ▼
③ 큐레이션 (Claude)      같은 개체가 여러 이메일에 흩어진 걸 병합, 모순 판단(동명이인 등)
        │                판단 못 하면 이슈/에 기록하고 문서엔 "미확정"으로 남긴다
        ▼
④ wiki 문서 작성         TEMPLATE.md 스키마대로 entities/sources/concepts에 .md 생성
        │                status: draft. entities: 필드는 정답지(추출 품질 검증용)
        ▼
⑤ 사람 리뷰              draft → reviewed. 리뷰 전엔 색인 안 한다
        │
        ▼
⑥ 색인 (시드 스크립트)    status: reviewed인 문서만, 프론트메터 제거, POST /documents/text
        │                scripts/lightrag-wiki-seed.py (작성 완료, 실행은 아직)
        ▼
⑦ LightRAG 내부 추출      LUNA(LLM)가 위키 문서에서 개체·관계를 또 한 번 뽑아 그래프로 적재
        │                — 여기서부터는 우리 손을 떠난 LightRAG 내부 동작
        ▼
⑧ 그래프 RAG 질의응답     /query, WebUI, 사이트 LightRAG 탭
```

## 왜 ②③④가 따로 있나

원본을 LightRAG(⑦)에 바로 넣으면 [2026-08-25-청킹-인덱싱-관찰.md](../2026-08-25-청킹-인덱싱-관찰.md)에서
실측한 문제가 그대로 재현된다 — 영문화, 서명·주소 노이즈, 날짜가 검색에 안 걸림,
동명이인 미판별. ②③④는 이걸 사람이 검증 가능한 형태로 한 번 거르는 단계다. 즉
wiki 문서는 "1차 추출 결과물"이자 동시에 LightRAG(2차 추출, ⑦)의 정제된 입력이다.
