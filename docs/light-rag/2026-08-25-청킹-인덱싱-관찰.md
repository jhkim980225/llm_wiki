# LightRAG 청킹·인덱싱·검색 연관 관찰 — 2026-08-25

원본 이메일(`.eml`) 3통을 LightRAG에 직접 색인하고, 청킹·개체추출·질의 응답을
단계별로 실측한 기록. 기존 색인 32건(위키 문서)에 추가로 넣어 **원본 이메일과
정제된 위키 문서가 같은 그래프에서 어떻게 다르게 다뤄지는지** 본다.

대상: `datafile/sj-help_보낸메일함/Files/` 의 3건
환경: LightRAG core 1.5.6 · `jh-wiki-graph` NodePort 31930 · LUNA(gpt-5.6-luna) + embeddinggemma 768d

---

## 1. 무엇을 넣었나

`.eml`은 MIME이라 그대로 못 넣는다. Python `email` 모듈로 파싱해 **헤더 4줄 + 본문 평문**
형태로 만들어 `POST /documents/text`에 보냈다. 첨부파일은 파싱하지 않았다.

```
# {Subject}

From: {From}
To: {To}
Date: {Date}

{본문 평문}
```

| 이메일 | 원본 | 투입 텍스트 | 첨부 |
|---|---|---|---|
| 럽앤다이브 아로마 롤온 라벨 문안 검수 | 22,900B | 2,873자 | 0개 |
| 성진 할랄인증 신청서 제조사 작성 파일 송부 | 15,443B | 3,163자 | 0개 |
| 성진 발주서 송부 | 176,150B | **367자** | 1개 (PDF) |

**발주서 메일이 이 표의 핵심이다.** 원본 176KB 중 실제 텍스트는 367자뿐이고, 발주 내용
(품목·수량·단가)은 전부 첨부 PDF에 있다. 본문은 "첨부파일 확인 부탁드립니다"와 서명뿐이다.
**첨부를 파싱하지 않으면 이 메일은 정보가 거의 없는 껍데기로 색인된다.**

## 2. 청킹 — 1,200토큰 고정 분할 + 100토큰 오버랩

k8s env에 청크 설정이 없어 LightRAG 기본값을 쓴다. 실측 청크 경계:

| 문서 | id | 청크 | 토큰 |
|---|---|---|---|
| 럽앤다이브 (2,873자) | `doc-1228bc82…` | 2 | `[1200, 584]` |
| 할랄인증 (3,163자) | `doc-f0a59810…` | 2 | `[1200, 281]` |
| 발주서 (367자) | `doc-f16d94f6…` | 1 | `[212]` |

기존 위키 문서도 같은 규칙이다 — `[1200, 1200, 816]`, `[1200, 1128, 28]` 처럼
**앞 청크를 1,200토큰으로 꽉 채우고 나머지를 뒤로 흘린다.**

오버랩이 눈에 보인다. 럽앤다이브 문서에서:

```
chunk-000  1,200토큰 / 1,913자   꼬리: "…호호바씨오일, 필리핀오렌지껍질오일, 라벤더오일…"
chunk-001    584토큰 / 1,090자   머리: "…호호바씨오일, 필리핀오렌지껍질오일, 라벤더오일…"   ← 반복
합계       1,784토큰 / 3,003자   (원문 2,873자 + 오버랩 130자)
```

**의미 경계를 보지 않는다.** 토큰 수만 세서 자르므로 표 중간·문장 중간에서도 끊긴다.
`[1200, 28]`처럼 뒤 청크가 28토큰짜리 부스러기로 남는 경우도 있다.

### 청킹의 실제 대가 (2026-08-24 실측)

전체 문서에서 "가장 많이 납품한 수량"을 묻자 **틀린 답**을 냈다.
표의 행들이 서로 다른 청크로 흩어져 "전체에서 최대"를 판단할 근거가 한 청크에 안 모인다.
단일 사실("앰플 10ml 개당 단가")은 한 청크 안에 있어 정확했다.

> 집계·비교 질문(최대·합계·전체)에 고정 청킹이 불리하다.

## 3. 인덱싱 — 청크당 LLM 2회, 개체·관계 추출

색인은 백그라운드 처리다(`status: processing → processed`). 실측:

| 문서 | 소요 | 청크 | LLM 호출 | 개체 증가 |
|---|---|---|---|---|
| 럽앤다이브 (2,873자) | 57초 | 2 | 4회 | **+48** |
| 할랄인증 (3,163자) | 62초 | 2 | 4회 | +20 |
| 발주서 (367자) | 31초 | 1 | 2회 | +3 |

**청크당 정확히 LLM 2회**다 — 1차 추출 + gleaning(빠뜨린 개체 재확인). 문서 크기와 무관하게
청크 수에만 비례한다. 기존 위키 문서도 동일: 3청크 문서는 6회, 1청크 문서는 2회.

캐시 전체 구성(35문서 기준, 285건):

```
extract  196   개체·관계 추출 (색인)
summary   49   같은 개체 설명 병합
query     26   질의 응답
keywords  14   질의 키워드 추출
```

**비용의 86%가 색인에서 나온다.** 문서당 약 7회(245/35). 18만 건 환산 시
`검토.md`의 "수백만 원" 추정이 이 수치로 뒷받침된다.

### 무엇이 개체가 되나 — 원본 이메일의 문제

럽앤다이브 이메일 1통(2,873자)에서 개체 48개가 나왔다. **44개(91.7%)가 영어다.**

```
원문(한글)              추출된 개체(영어)
호호바씨오일        →   Jojoba Seed Oil · Jojoba Oil (Refined) · Jojoba Oil Data
단향오일            →   Sandalwood · Sandalwood Extract · Sandalwood Oil
라벤더오일          →   Lavender Oil
토코페릴아세테이트  →   Tocopheryl Acetate · Tocopherol
```

세 가지 문제가 겹친다.

1. **영문화** — 순한글 원문인데 원문에 없는 영어 단어를 만든다. `SUMMARY_LANGUAGE`
   미설정으로 기본값(영어)을 쓰기 때문. 위키의 `호호바씨오일` 문서와 **영원히 연결되지 않는다.**
2. **분신** — 같은 대상이 표기 변형마다 노드가 된다. 주소 하나가 5개로 갈라졌다:
   `경기도` / `경기도 남양주시` / `Namyangju` / `Namyangju-si` / `Gyeonggi-do`
3. **개체 아닌 것** — 서명 블록과 각주가 개체가 된다: `10 Milliliters`, `CAS No.`,
   `USCAS No.`(원문 `US\nCAS No.` 줄바꿈이 붙은 오타), `Bubblebank Website`

**정제된 위키 문서를 넣을 때와 다르다.** 할랄인증 메일은 +20개, 발주서 메일은 +3개
(`(주)썬화인글로벌`·`송규진`·`화장품 R&D` — 전부 한글)로 상대적으로 깨끗하다.
본문이 짧고 이름 위주라 번역할 거리가 없었기 때문이다.

### 그래도 기존 그래프에는 붙는다

새 노드를 고립시키지 않는다. 럽앤다이브 색인 후 기존 `정아라` 노드의 관계가
**162 → 187개로 늘었다.** 새 개체 `김민경`도 기존 그래프에 물렸다:

```
The Publisher              --[employment, representation]--> 김민경
Label Copy Review Request  --[review, submission]-->         김민경
Jojoba Oil Data            --[material data, submission]-->  김민경
Fragrance Ratio Excel File --[ingredient data, submission]--> 김민경
```

관계마다 `file_path`로 출처가 추적된다.

## 4. 질문했을 때 어떤 연관을 가져오나

### 단일 문서 사실 — 정확하다

```
Q. 타임리커버리 EGF 세럼의 영문 전성분 앞 5개는?          [naive · 3.5초]
A. Water, Glycerin, Butylene Glycol, PEG/PPG-17/6 Copolymer, Niacinamide   OK
근거: 20260716-성진-할랄인증-…                              (1건, 방금 넣은 이메일)
```

```
Q. 썬화인글로벌에 무엇을 보냈고 담당자는 누구인가?         [naive · 11.1초]
A. 발주서 · 발신 정아라 연구원 / 수신 송규진 팀장 · 2026-07-15   OK
근거: 20260715-성진-발주서-송부 + 정아라-2026년-7월-업무    (신규 이메일 + 기존 위키)
```

두 번째가 특히 좋다. **방금 넣은 이메일과 기존 위키 문서를 함께 근거로 썼다.**
이메일에서 담당자를, 위키에서 날짜 맥락을 가져왔다.

메일 헤더 `From: 김종태`인데 본문 서명은 `정아라`다. **본문을 우선해 정아라로 답했다** — 맞다.

### 모드별 차이 — 답변 품질에는 거의 영향 없다

같은 질문("레스트 롤온 전성분")을 5개 모드로:

| 모드 | 시간 | 성분 정확도 | 영문 오염 |
|---|---|---|---|
| naive | 6.2s | 7/7 | 0 |
| local | 6.1s | 7/7 | 0 |
| global | 6.8s | 7/7 (+ 단향추출물 표기 변형 언급) | 0 |
| hybrid | 6.2s | 7/7 | 0 |
| mix | 5.2s | 7/7 | 0 |

**개체가 영어로 뽑혀도 답변은 한글로 정확하게 나온다.** 모든 모드가 생성 단계에서
원문 청크를 함께 넘기기 때문이다.

> 영문화가 해치는 것은 **답변이 아니라 그래프 연결**이다. 위키 문서와 이으려 할 때만 문제가 된다.

### 교차 문서 질문 — 여기서 실패했다

```
Q. 정아라가 2026년 7월 15~16일에 처리한 업무를 모두 정리해줘   [hybrid · 8.0초]
근거: 정아라-2026년-7월-업무   (1건 — 기존 위키 문서만)

A. "7월 15일: 럽앤다이브 라벨 문안 검수, 코바상사 할랄인증, 에코스팜 발주,
    썬화인글로벌 발주서 송부…
    7월 16일 업무는 별도로 확인되지 않습니다."
```

**틀렸다. 7월 16일자 이메일을 2통 갖고 있다** (할랄인증 11:12, 럽앤다이브 15:35).
`naive`로 바꿔도 같았다 — 근거가 위키 문서 2건이고 이메일은 하나도 안 걸렸다.

원인으로 보이는 것:

- 이메일의 날짜는 헤더에 `Date: Thu, 16 Jul 2026 15:35:27 +0900` 형태로만 있다.
  본문에 "7월 16일"이라는 한국어 표현이 없어 **질의 임베딩과 가깝지 않다.**
- 개체 추출에서 **날짜가 개체로 안 잡혔다.** 새 개체 48개에 날짜가 없다.
- 반면 기존 위키 문서 `정아라-2026년-7월-업무`는 제목·본문에 날짜가 한국어로 정리돼 있어
  강하게 걸린다. **정제된 요약 문서가 원본을 이긴다.**

역설적으로 그 위키 문서가 "7월 15일 럽앤다이브 라벨 문안 검수"를 이미 담고 있어서
**답 자체는 대체로 맞았다.** 원본 이메일이 없어도 답이 나온 것이고,
이번에 넣은 이메일 3통이 그 답에 기여한 바는 없다.

### 관계 질문 — 신규·기존이 섞여 나온다

```
Q. 성진이 최근 연락한 외부 담당자와 각각 무슨 건인가?         [hybrid · 11.7초]
근거 4건: 20260715-성진-발주서-송부              <- 신규 이메일
          김종태-대표이사의-주요-의사결정과-…      <- 기존 위키
          주간-업무내역-2026-07-27-2026-08-02-5   <- 기존 위키
          주간-업무내역-2026-07-27-2026-08-02-2   <- 기존 위키

A. 송규진 팀장(㈜썬화인글로벌) — 발주서 송부 건, 2026-07-15, 정아라가 전달
   그 밖에 선일상사 향료 발주, 바이오스펙트럼 납기, 코바코스메틱 생산·포장,
   정재윤테라피 라벨 입고 건이 있으나 담당자 개인 성명은 특정되지 않음
```

**이름·소속이 함께 있는 개체는 원본 이메일에서만 나왔다.** 위키 요약 문서에는
거래처명만 있고 담당자 성명이 없다. 원본 이메일을 넣은 값어치가 여기서 나온다.

## 5. 정리

**청킹**
- 1,200토큰 고정 + 100토큰 오버랩. 의미 경계를 안 본다
- 문서당 청크 수 = LLM 비용의 유일한 변수
- 집계·비교 질문에 불리 (표가 청크 경계로 갈린다)

**인덱싱**
- 청크당 LLM 2회 고정. 문서당 평균 7회(summary 병합 포함)
- 비용의 86%가 색인. 질의는 14%
- 원본 이메일은 개체의 90%가 영어·분신·서명 조각. 정제된 문서보다 품질이 나쁘다
- 그래도 기존 노드에는 정상적으로 연결된다 (`정아라` 관계 162→187)

**검색 연관**
- 단일 문서 사실: 정확. 신규 이메일이 근거로 잘 잡힌다
- 담당자 성명·소속 같은 **원본에만 있는 세부**: 원본 이메일이 유일한 출처로 값어치가 있다
- 날짜 기준 교차 질문: **실패.** 헤더 날짜가 검색되지 않아 이메일이 안 걸린다
- 모드(naive~mix)는 답변 정확도에 거의 영향 없음. 속도도 5~12초로 비슷

**첨부파일**
- 발주서 메일처럼 실질 정보가 PDF에 있는 경우 본문만으로는 껍데기다.
  176KB 원본에서 367자만 색인됐다

## 재현 방법

```powershell
# 색인 (LightRAG API 직접 — 개발 PC에서 31930 접근 가능)
POST http://192.168.0.103:31930/documents/text
  X-API-Key: lightrag-poc-sj-2026
  {"text": "<파싱한 이메일 텍스트>", "file_source": "eml/<slug>"}

# 상태·청크·개체 확인
GET /documents            # status, chunks_count, content_length
GET /graph/label/list     # 개체 라벨 전체
GET /graphs?label=정아라&max_depth=1&max_nodes=3000

# 내부 저장소 (LLM 호출 수·청크 경계)
kubectl exec -n jh-wiki-graph deploy/lightrag -- python -c "..."
  /data/kv_store_text_chunks.json          청크 본문·토큰 수
  /data/kv_store_llm_response_cache.json   호출 이력 (cache_type: extract/summary/query/keywords)
```

질의는 사이트 `LightRAG` 탭(bench 계정) 또는 `POST /api/lightrag {"query","mode"}`.
