# wiki/ 색인 후 질의 테스트 — 2026-08-29

`scripts/lightrag-wiki-seed.py`로 처음 색인한 `wiki/` 문서 5건에 대해 LightRAG API에
직접 질의해 사실 정확도를 확인하고, 위키링크(`[[id]]`) 구문이 그래프에 그대로
개체로 오염되는지 실측했다. [파이프라인.md](wiki/파이프라인.md) ⑧단계.

환경: LightRAG core `jh-wiki-graph` NodePort 31930 · LUNA(gpt-5.6-luna) + embeddinggemma.
색인 대상: `amicos`·`arabko`·`b-mote`·`barunweb`·`bio-fdnc` (전부 `status: reviewed`,
2026-08-29 `--limit 5`로 색인, 전부 `processed` 확인 — [운영.md](운영.md) 색인 이력 참조).

## 2. 위키링크(`[[id]]`) 오염 체크 — 문제없음

`wiki/` 문서 본문엔 `[[seongjin]]`, `[[fyc-company]]` 같은 위키링크 구문이 그대로
들어있다. 시드 스크립트는 이걸 별도 처리 없이 그대로 전송하는데, LUNA가 이 대괄호
구문 자체를 개체로 잘못 뽑을 위험이 있어 확인했다.

```
전체 라벨 수: 2,149
[[ ]] 포함 라벨: 없음 (0건)
```

**결과: 오염 없음.** LUNA가 `[[seongjin]]`을 개체명이 아니라 문맥으로 처리하고
"성진"이라는 실제 개체만 뽑아낸 것으로 보인다. 위키링크 구문을 색인 전에 벗겨낼
필요는 없어 보인다 — 다만 표본 5건뿐이니 규모가 커지면 재확인할 것.

## 3. 부수 발견 — 기존 그래프의 "성진" 표기 분신이 심하다

이번 신규 5건과 무관하게, 전체 라벨(2,149개) 중 "seongjin"/"성진"을 포함한 것만
뽑아보니 **70개 넘게** 나왔다. 신규 5건은 각각 `[[seongjin]]` 링크 텍스트로만
"성진"을 언급했을 뿐인데(성진 자체는 이번에 색인 안 함), 기존에 이미 색인돼 있던
34건(운영 위키 32건 + 이메일 2~3건)이 이 정도 규모의 분신을 만들어놨다.

표기 변형 일부:
```
Seongjin / 성진 / (주)성진 / 주식회사 성진 / Seongjin Co., Ltd. / 성진 주식회사
Seongjin CEO / Seongjin Employee / 성진 대표이사 / 성진 직원
seongjin (소문자)
```

거래처·문서 제목이 라벨로 잡힌 것도 다수 섞여 있다(`[성진] 발주서 송부의 건` 같은
이메일 제목 자체가 하나의 "개체"로 추출됨) — 이건 [2026-08-25 관찰](2026-08-25-청킹-인덱싱-관찰.md)에서
이미 지적한 문제와 같은 패턴이다.

동명이인 소지가 있는 라벨도 보인다 — `박성진`, `추성진`처럼 "성진"이 들어간 다른
사람 이름이 회사 "성진"과 그래프상 인접해 있을 수 있다. 이번 검토 범위 밖이라
직접 확인은 안 했다.

**결론**: 신규 5건은 깨끗하게 들어갔지만, **기존 34건 쪽의 개체 분신 문제가 여전히
크다.** `wiki/`로 정제해 새로 넣는 문서가 늘어날수록 "성진" 표준 개체 하나로
합쳐지는 게 아니라, 기존 분신들 옆에 또 하나의 표기가 추가되는 구조라 — 전량
재색인(기존 34건 삭제 후 정제된 wiki/ 문서로만 재구성) 없이는 이 문제가 저절로
안 풀린다.

## 4. 다음에 확인할 것

1. `wiki/` 문서를 더 색인해서 "성진" 라벨이 기존 분신 중 하나에 합쳐지는지, 아니면
   또 다른 변형(`seongjin`)만 늘리는지 — 이번 5건은 성진 자체를 안 넣어서 검증 못 함
2. 기존 34건(운영 위키 원본) vs `wiki/`(정제본)를 같은 그래프에 공존시킬지, 기존
   걸 지우고 `wiki/`로만 재구성할지 결정 필요 — `검토.md`에서 이미 논의된 "전량
   재색인" 질문과 연결됨
3. `박성진`·`추성진` 같은 라벨이 실제 동명이인인지, 진짜 "성진" 브랜드 데이터의
   일부인지 확인
