### 코드 병목 감사 및 처리 (오픈클로 작업)

핫패스에서 대상 링크마다 개별 쿼리를 돌리던 N+1과, 저장 응답을 막던 임베딩 호출을 걷어냈다. 온톨로지 허브 문서(inLinks/outLinks 수백 개)에서 특히 컸다.

**N+1 → 배열 연산 한 방 (2N 왕복 제거)**
- `src/lib/pages/save.ts` `syncBacklinks`: 대상마다 findUnique+update → `array_remove`/`array_append` raw UPDATE 2개
- `src/lib/pages/rename.ts`: 참조자 개별 findUnique → `findMany` 1회 + 대상 백링크 `array_replace` 1쿼리
- `src/app/api/pages/[slug]/route.ts` DELETE: 대상 루프 → `array_remove` 1쿼리
- `src/lib/agent/tools.ts` `wiki_delete_page`: 동일 배치화

**저장 지연 제거**
- POST/PUT 페이지 라우트의 embed-on-save를 `await` → `void`(fire-and-forget). 저장 응답이 더 이상 임베딩(Ollama 왕복 ~수백 ms)을 기다리지 않음. 실패는 여전히 삼킴

**순차 → 병렬**
- `GET /api/pages/[slug]`: 백링크·죽은링크 조회 `Promise.all`
- `src/lib/rag/compose.ts` `searchWiki`: 용어별 content 풀스캔(각 수백 ms)을 순차→`Promise.all` 병렬. dedup은 용어 순서 유지로 우선순위 보존. /ask 근거수집 벽시계 = k×→1×

**검증**: 전체 173개 테스트 통과 + `tsc --noEmit` 클린. 백링크 동기화·rename·delete 동작 동일(테스트로 확인)

**손 안 댐(의도적)**: 검색 부분문자열 byContent ~320ms(문서상 20만 행 전에는 pg_trgm 보류) · 그래프 RAG 생성 210초(32B 모델속도, 모델 바운드)
