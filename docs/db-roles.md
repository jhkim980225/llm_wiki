# 그래프 DB와 RDB의 역할 분담

2026-08-06 작성. "왜 그래프 DB 기반인데 Postgres를 쓰는가"에 대한 정리입니다.
구조도는 `docs/architecture.md` 참조.

## 한 줄 요약

> **답을 만들 때는 그래프 DB를 조회하고, 보여줄 때는 Postgres를 조회한다.**
> 그래프 DB(Fuseki)는 지식의 원본이자 질의 엔진이고, Postgres는 위키 화면과
> 편집을 위한 작업 저장소입니다.

## 1. 그래프 DB (Fuseki) 의 역할

사내 3개 소스(ejkim 이메일 온톨로지 · seunghoon 온톨로지 · kakao 지식그래프)를
타 팀이 운영합니다. 이 프로젝트에서는 **읽기 전용**입니다.

### 1.1 지식의 원본 (Source of Truth)

개체·관계의 진실은 Fuseki에 있습니다. Postgres에 있는 적재본은 언제든 재적재로
다시 만들 수 있는 사본이며, 그 반대는 성립하지 않습니다.

### 1.2 실시간 지식 질의 (SPARQL)

도우미(/chat)와 AI 작성(/ask)이 질문을 받으면 LLM이 그래프 조회 도구를 선택하고,
앱이 SPARQL을 만들어 **Fuseki에 직접** 질의합니다. Postgres 사본을 거치지 않습니다.

- 예: "코바상사와의 거래 건수는?" → ejkim 소스 SPARQL → 이메일 32건 → LLM이 답변 작성
- 사본 대신 원본에 묻는 이유: 사본은 적재 시점의 스냅샷이라 낡을 수 있고,
  정확한 수치·최신 관계는 원본이 맞습니다.

### 1.3 그래프 DB가 아니면 안 되는 질의

| 능력 | 설명 | RDB로 하면 |
|---|---|---|
| 관계 순회 | "코바상사와 몇 단계를 거치든 연결된 모든 개체" — SPARQL property path 한 줄 | 깊이마다 JOIN 추가 또는 재귀 CTE, 관계 종류가 늘면 재작성 |
| 스키마 없는 확장 | '발주'·'견적'·'테스트결과' 등 새 관계 타입이 생겨도 트리플 모델은 변경 없음 | 관계 타입마다 마이그레이션 |
| 사내 표준 접점 | RDF/SPARQL은 W3C 표준. 세 팀이 이미 이 형식으로 지식을 발행 중 | 팀마다 스키마 협상 필요 |
| (온톨로지) 타입 추론 | 클래스 계층 기반 추론 | 없음 |

## 2. RDB (Postgres) 의 역할

위키 앱의 단일 작업 저장소입니다. `Page`(문서) · `PageRevision`(수정 이력) ·
`Folder`(트리) 세 테이블, 현재 약 221 MB (99%가 온톨로지 적재본).

### 2.1 문서 저장과 편집

- 마크다운 본문, 제목, 요약, `[[링크]]` 파싱 결과(outLinks/inLinks)
- **낙관적 잠금** (version — 동시 편집 충돌 감지), **리비전** (수정 전 스냅샷),
  **soft delete + 휴지통** (7일 보관)
- SPARQL Update에는 버전·트랜잭션·이력 개념이 없어 그래프 DB로는 재발명이 필요합니다.

### 2.2 검색

- 한국어 부분문자열 검색 + 랭킹 (Ctrl+K)
- **의미검색** — pgvector 임베딩(768차원) + hnsw 인덱스. 단어가 안 겹쳐도 뜻이
  가까운 문서를 찾습니다. Fuseki(Jena)에는 벡터 인덱스가 없고, 텍스트 인덱스
  설정 권한도 우리에게 없습니다(타 팀 인프라).

### 2.3 화면 조회 전담

문서 열기, 트리, 검색, 그래프 뷰(/graph)는 전부 Postgres에서 끝납니다.
매 클릭마다 원격 SPARQL 왕복을 하지 않기 위해서입니다.

- 실측: SPARQL 전량 조회 24,822건 = **36초**. 같은 규모 Postgres 스캔 = **수백 ms**
- 그래프 뷰의 노드·에지도 Fuseki가 아니라 `Page.outLinks`에서 계산합니다
  (문서 트리와 같은 기준 — 적재본 제외, 연결 상위 200개만 렌더)

## 3. 적재(/sources)는 왜 필요한가

"질의는 어차피 Fuseki에 직접 하는데 왜 가져오나?" — 적재는 **질의용이 아니라
열람용**입니다. 이 앱의 컨셉이 "개체를 그래프로 그리지 않는다, 개체가 문서다"
이므로, 개체를 문서로 만들려면 가져와야 합니다.

적재가 없으면 죽는 것:

1. **개체 열람** — `ejkim/코바상사`를 문서로 열고 `[[링크]]`로 관련 개체를 타고
   다니는 것. SPARQL은 질문→답만 주고 브라우징이 안 됩니다.
2. **AI 문서의 근거 링크** — /ask가 만든 문서는 `[[ejkim/…]]` 근거 링크를 담는데,
   대상 문서가 존재해야 링크가 살아 있습니다 (없으면 평문으로 강등 처리).
3. **개체 검색** — 검색창·의미검색에 개체가 걸리려면 Postgres에 있어야 합니다.
4. **백링크·그래프 뷰** — "이 문서를 가리키는 문서"는 전체를 미리 훑어 계산해두는
   정보라 데이터가 손안에 있어야 합니다.

적재를 안 해도 도우미의 SPARQL 질의는 정상 동작합니다. 위키에 개체 문서가
없을 뿐입니다.

### 편집 보호

재적재 시 `lastEditSource = 'ontology'`인 문서만 갱신합니다. 사람·AI가 고친
문서는 덮지 않습니다.

## 5. 선례 — Wikidata도 같은 구조

세계 최대 지식그래프인 Wikidata의 구조:

- 원본 데이터: **MariaDB** (RDB) — 편집·버전 관리 전부 여기
- SPARQL 질의: **Blazegraph** 트리플스토어 — 원본에서 변경 스트림을 받아
  유지되는 **파생 인덱스**
- 검색: Elasticsearch 별도

즉 "그래프 기반 제품 = 모든 저장이 그래프 DB"가 아니라, 그래프 DB는 관계 질의
엔진으로 쓰고 문서·이력·검색은 적합한 저장소에 두는 것이 표준 패턴입니다.

- [Wikidata Architecture Overview (addshore)](https://addshore.com/2018/12/wikidata-architecture-overview-diagrams/)
- [Wikidata Query Service (Wikitech)](https://wikitech.wikimedia.org/wiki/Wikidata_query_service)
- [WDQS backend update (Wikidata)](https://www.wikidata.org/wiki/Wikidata:SPARQL_query_service/WDQS_backend_update)

## 6. 남은 갭과 로드맵 — 역반영

현재는 흐름이 단방향(Fuseki → Postgres)입니다. 위키에서 만든 문서·관계가
그래프로 돌아가지 않으므로, "그래프 = 모든 지식의 진실"이 완성되려면
**역반영**이 필요합니다.

- 계획: 위키 저장 시 문서·`[[링크]]`를 전용 Fuseki dataset(`ds` — 현재 비어 있음)에
  트리플로 기록 (SPARQL Update)
- 완성 시: 온톨로지 + 위키 지식 전부를 SPARQL로 질의 가능, 타 팀 도구와 연동
  가능, Postgres는 "그래프에서 재구축 가능한 화면 캐시"로 정리됨
- 기능정의서 3.3 장기 과제 항목

## FAQ

**Q. 왜 Postgres를 쓰나?**
문서 편집·이력·한국어 검색·의미검색은 그래프 DB가 못 하는 일이라서.

**Q. 왜 그래프 DB를 쓰나?**
관계 순회 질의와 사내 지식 표준 접점은 RDB가 못 하는 일이라서.

**Q. Fuseki 단일 저장소로 가면?**
의미검색·리비전·잠금·한국어 검색을 잃거나 전부 재발명해야 하고, 화면 조회가
매번 원격 왕복이 되며(전량 36초 실측), 타 팀 Fuseki 장애가 곧 위키 장애가
됩니다. 잃는 것 대비 얻는 것이 없어 채택하지 않았습니다.

**Q. 열람도 그래프 DB에서 직접 하면 안 되나?**
개체 하나를 즉석 렌더하는 것은 가능하나(RDF 뷰어 방식), 편집·백링크·검색·링크
타기 같은 "위키의 열람"은 데이터가 로컬에 있어야 성립합니다.
