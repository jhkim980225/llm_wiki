# GraphWiki 시스템 점검 — 분석 보고서 및 개선 Plan

## Context

주요 기능 구현이 어느 정도 끝난 시점에서, **실제 서비스로 쓰기에 얼마나 완성되어 있는지**를 확인해 달라는 요청.
리팩터링이 목적이 아니라 빠진 기능·구조적 문제·잠재 버그·보안·UX·운영 문제를 실측으로 찾는 것이 목적이다.

이 문서의 모든 항목은 **실제 코드 읽기 + 운영 서버 실측**으로 확인했다. 추측은 "미확인"으로 표시했다.
조사 기준: 작업트리 현재 상태, 배포 버전 `0.67.0`, 운영 DB 실측(2026-08-10).

작성 시점에 **코드는 수정하지 않았다** — 발견과 우선순위 정리가 목적이다.
후속 수정은 15장의 P0~P3 순서를 따르고, 처리한 항목은 이 문서에 완료 표시를 남긴다.

> **2026-08-10 조치 완료: P0-1 · P0-2 · P0-3** (아래 15장 참조).
> 8장의 Critical 3건(C-1·C-2·H-1)이 해소됐다. **C-3(로그아웃이 쓰기를 막지 못함)은 남아 있다** — P1-1.

## 요청 흐름

```
사용자 브라우저
  → [Ingress 3종] cloud.fedaground.com/graphwiki (TLS) · wiki.1.201.66.21.nip.io (평문 HTTP) · NodePort 31900
  → [middleware.ts] 세션 쿠키 HMAC 서명+만료만 검증 (DB 조회 없음)
       ├ 실패 → API는 401 / 페이지는 /login 리다이렉트
       └ 통과 ↓
  → [Route Handler] src/app/api/**/route.ts (49개)
       ├ requireSession() 있는 라우트(29개) → DB로 세션 폐기·사용자 상태 재확인
       └ 없는 라우트(20개) → 그대로 실행
  → [lib 순수 모듈 + Prisma]
  → [외부] Fuseki / RAG API / LLM / 임베딩 / PlantUML
  → 응답 (JSON 또는 NDJSON 스트림)
```

핵심 설계 원칙은 지켜지고 있다 — 로직은 I/O 없는 순수 모듈(`lib/wiki/*`, `lib/ontology/build.ts`)에 있고 Route Handler가 호출한다. 테스트가 Prisma·Next를 안 거치는 구조도 유지된다.

# 3. 기능 누락

## P0 — 서비스 사용에 반드시 필요

| 기능 | 왜 필요한가 |

| 기능 | 왜 필요한가 |
|---|---|
| **비밀번호 변경 화면** | API(`api/auth/change-password`)는 있으나 호출하는 UI가 없다. `mustChangePassword` 플래그도 UI에서 처리되지 않는다 |

# 4. 사용자 흐름 점검 (실측)

운영 서버에 직접 요청해 확인한 결과.

| 시나리오 | 결과 |
|---|---|
| 비로그인 → `/graphwiki/flow` | 307 → `/login` **정상** |
| 비로그인 → `/graphwiki/api/pages/*` | 401 **정상** |
| 로그인 | 200 + 쿠키 발급 **정상** |
| 존재하지 않는 문서 | 문서 없음 화면 + "그래프에서 만들기" **정상** |
| 존재하지 않는 라우트 `/graphwiki/foo` | 셸은 뜨지만 **안내 문구 없음**(not-found.tsx 부재) |
| **잘못된 URL 인코딩** `/wiki/kakao/%ZZ` | **흰 화면 "Internal Server Error"** — 앱 셸도 없고 돌아갈 링크도 없음 |
| API 동일 케이스 | **500**(400/404가 아님) |
| 로그아웃 | `window.location.href = '/login'` — basePath 누락으로 **전체 로드 + 서버 리다이렉트 왕복** |

# 5. Frontend 점검

## 구조

- **라우트 12개**, `'use client'` **27개 파일**. 서버 컴포넌트는 `layout.tsx`·`graph/page.tsx`·`wiki/page.tsx` 3개뿐이고, `layout.tsx`가 최상위를 client `Vault`로 감싸므로 **모든 페이지가 사실상 클라이언트 트리** 안에 있다.
- 데이터 페칭이 전부 마운트 후 `useEffect` → 초기 렌더는 항상 빈 화면. 서버 컴포넌트 페칭 0건.
- 대형 파일: `EntityGraph.tsx` 667 · `PageEditor.tsx` 658 · `ask/page.tsx` 441 · `FileTree.tsx` 429 · `flow/page.tsx` 352. `globals.css` 4,397줄 단일 파일.

## Next.js 특수 파일

| 파일 | 존재 |
|---|---|
| `layout.tsx` · `template.tsx` | 있음 |
| **`error.tsx` · `not-found.tsx` · `loading.tsx` · `global-error.tsx`** | **전부 없음** |

렌더 예외를 잡는 경계가 하나도 없다. Suspense 경계도 없어 대안도 없다.

## 상태·요청

- **중복 호출**: `/api/graph-ref?all=1`(개체 타입 전량)을 `ChatPage`와 `DocChatPanel`이 각각 요청하고, `DocChatPanel`은 `key={slug}`라 **문서 이동마다 재요청**. `/api/flow`는 `/flow`·`/calendar`가 각각. `/api/folders`는 대화상자를 열 때마다.
- **stale 가드**: 6곳 있음 / **없는 곳 12곳** — 그중 가장 자주 밟히는 문서 본문 로드에 없다(위 4장).
- **AbortController: 클라이언트 0건.** 스트리밍 3종(`compose`/`chat`/`verify`) 모두 취소 불가.

## UX

- **중복 클릭 방지 누락**: `flow/page.tsx:240`(등록), `wiki/[...slug]/page.tsx:225`(만들기), `FileTree.tsx:332,335`(새 문서/폴더), `Dialog.tsx:78`(확인 — `await run()` 중 활성 유지), `PageEditor.tsx:627,630,636`(복제/내보내기/삭제). **연타하면 문서·폴더·FLOW가 중복 생성된다.**
- **네이티브 `confirm()` 4곳 잔존**(`trash:45`, `chat:62`, `flow:134`, `wbs:120`) — 앱 공통 대화상자와 혼재.
- **토스트 사용은 4개 파일뿐** — 나머지는 인라인 notice. 같은 성격 피드백의 표현이 화면마다 다르다.
- **모달 4종 전부 `role="dialog"`·`aria-modal`·포커스 트랩 없음.** `Markdown` 미리보기·`flow` 상세는 Escape로도 안 닫힌다.
- **모바일 미대응**: 캘린더 7열 고정(미디어 쿼리 없음), `/verify` 인라인 `1fr 1fr` 하드코딩, `.wbs-table` 가로 스크롤 없음.
- 잘한 점: 전역 `:focus-visible`, `IconButton`의 `label`이 **타입상 필수**, `aria-hidden` 89개 일관 적용, 트리 키보드 탐색.

## 잘 되어 있는 것

- **근거**: 운영 DB 실측(`WORKSPACE_ADMIN`, 4자 비밀번호), 공인망 로그인 성공
- **조치**: 사용자 선택에 따라 계정은 유지하고 **비밀번호만 16자 랜덤으로 교체**(bcrypt cost 12) + 전 세션 폐기(141건).

- **남은 것**: `sungjin` 비밀번호 강도는 확인하지 않았다(해시만 정상 확인).
